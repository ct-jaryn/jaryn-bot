---

## 0. 一句话结论

| 口径 | 还差 | 判断 |
|---|---|---|
| **你自己定的标准**（无语音；多 bot 交流 / 记忆 / 主动搜索完成任务） | **7–10 周可用，4–5 个月好用** | ✅ 设计已覆盖 80%，剩下是写代码 |
| **个人版对标 Grok Bot**（含浏览器/跨应用/凭据/多通道） | **6–8 个月** | ⚠️ 缺浏览器与凭据两块硬骨头 |
| **同品类产品**（三端 App、团队 Bot、会议、模板市场、计费） | **10–14 个月** | ❌ 不是 solo 项目该追的目标 |
| **企业级替代**（SAML/SCIM/网络策略/审计/合规） | **16–24 个月** | ❌ 需要团队与合规投入 |

**差距不在功能清单，在四件事**：① 90%→100% 的可靠性；② 凭据/审批这套信任工程；③ 分发与 UX；④ 成本结构。

## 2. 按任务类型算"覆盖率"

比功能清单更有意义的算法：**Grok Bot 的真实使用场景，jaryn 什么时候能接住。**

| 任务类型（举例） | Grok Bot | jaryn v0.1（4–5 个月） | jaryn v0.2（+2–3 个月） | jaryn v1.0（+4–6 个月） |
|---|---|---|---|---|
| 研究 / 写作 / 文档 / 代码 / 定时简报 | ✅ | **75–85%** | 85–90% | 90% |
| 跨应用（Gmail/日历/Notion/CRM） | ✅ | 30%（要逐个接） | **55–65%**（MCP/Composio） | 75% |
| 网页操作（订票、报销、填表） | ✅ | <10% | 25–35%（Playwright） | **60–70%**（云浏览器） |
| 需要登录的流程 | ✅ | ~0% | ~0% | **30–40%**（Vault 后；支付网关不做，只填卡） |
| 团队协作（群聊、共享 Bot、会议） | ✅ | 15%（L1 内部协作） | 30% | **50–60%** |
| 企业管控 | ✅ | 0% | 0% | 10–20% |

> **结论**：如果 jaryn 的目标是"个人 AI 同事"，v0.1 已经能覆盖**最常用的一类**（研究/写作/代码/简报）；但 Grok Bot 最出圈的演示（订会议、报销、网页填表）**必须等浏览器 + 凭据**，这正是 6–8 个月差距的主体。

## 3. 四个真正的差距（不是功能列表）

1. **可靠性 90% → 100%**
   Grok Bot 公开承认这块是难点（mid-turn 暂停、跨镜像重建、断线不终结 turn），也出过事故。我们的设计有事件溯源 + resume + abort，但"长任务中断后续跑不重复副作用"要靠幂等键 + 混沌测试 + 真实使用打磨，**至少 2–3 个月的隐性工作量**。
2. **信任工程**
   审批语义（只有用户消息算指令）、凭据不落地（Vault/Secure Form）、防注入、审计。这是 Grok Bot 真正的护城河，也是它所有安全设计的落点。我们的 provenance + 策略引擎只是骨架。
3. **分发与 UX**
   三端 App、Bot 模板市场、拖拽式配置、通知与语音入口。IM-first 能省掉 App，但"像产品"和"像脚本"的差距在 3–6 个月。
4. **成本结构**
   Grok Bot 是"上下文税"驱动的低毛利生意（二手实测 20–25 万 token/轮）。我们自带 DeepSeek 成本优势，但**主动任务 + 多 Bot 会把 token 放大**，预算护栏和记忆压缩必须从第一天就当架构约束。

---

## 4. Grok Bot 的弱点 = 我们的机会

| Grok Bot 的弱点 | jaryn 的空间 |
|---|---|
| 一用户一 VM，一个 Bot 玩坏全名册停摆 | **任务级/线程级沙箱**（我们按 session 隔离），单点更小 |
| 不支持自托管/on-prem/BYO 镜像 | 自托管 + 数据不出门就是卖点 |
| 周额度不透明、VM 规格不公开 | 预算可见（token/费用/步数）、可自定 |
| 语言模型/供应商不可选 | 模型可插拔（DeepSeek/任意 OpenAI 兼容） |
| 上下文税导致额度紧张 | compaction + 检索 + 结构化记忆，成本可控 |
| 云 VM 数据中心 IP 被反爬拦 | 可选本地/家宽出口（Phase 2） |

**所以别做"Grok Bot 平替"，做"自托管、可审计、成本可控的个人 AI 同事"**——功能面 60–70% 就够打动目标用户，剩下 30% 是 Grok Bot 的包袱。

## 5. 从现在起的时间线

```
现在 ──► P0–P2（7–10 周）     单 Bot + 真模型 + Telegram/飞书 + 审批 + 文件
      ──► v0.1（4–5 个月）    L1 多 Bot + 记忆闭环 + 守夜人 + 插件体系
      ──► v0.2（+2–3 个月）   Playwright MCP + 连接器（Gmail/日历/Notion）+ Pages
      ──► v1.0（+4–6 个月）   云浏览器/云电脑 + Vault + 团队 Bot + Web UI
      ──► 企业级（+6–9 个月） SAML/SCIM/审计/多租户
```

**关键判断**：v0.2 的浏览器 + 连接器是"能不能对标"的门槛。越过它，个人版就成立；越不过，就永远只能做"聊天 + 写文档 + 查资料"的助手。

---

## 6. 建议

1. **先按自己的标准验收**：P0–P2 做完（7–10 周）就应该能回答"我愿不愿意每天用它"——这比任何对标百分比都有意义。
2. **v0.1 之前不要碰云电脑**：浏览器先上 Playwright MCP（外购），把"网页操作"从 10% 拉到 35%，成本是 2–4 周而不是 4 个月。
3. **v0.2 再决定要不要做云电脑**：如果 80% 的任务不需要"看屏/接管/登录"，就别做 VM 集群；需要再做（E2B/Daytona/自建 Firecracker 均可）。
4. **永远不追**：语音/会议/支付/X 集成/消费级 App。这些是 Grok Bot 的差异化，不是你的。
5. **把"可靠性 + 信任"当产品功能做**：预算面板、审批记录、记忆查看/遗忘、任务回放——这些是自托管用户最买账的东西。

---

## 7. 一句话回答

**按你自己的标准：设计已到位，差写代码，7–10 周可用、4–5 个月好用。**
**按 Grok Bot 全产品：差 10–14 个月，其中一半是浏览器/云电脑 + 凭据，另一半是可靠性、UX 和企业能力；而那后半部分，恰恰是不该 solo 去追的。**
